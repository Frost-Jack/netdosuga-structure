# order-service

Independent Go module and Docker context. `go test ./...` runs unit tests; `TEST_DATABASE_URL=... go test -count=1 ./...` additionally exercises ownership, concurrency, idempotency, expiry and provider uncertainty in a disposable SQL schema. Docker builds run unit tests before compiling.

Startup requires `APP_ENV=local`, `MOCK_MODE=true`, `DATABASE_URL`. Defaults: `GRPC_ADDR=:50051`, `HTTP_ADDR=:8081`, `IDENTITY_BASE_URL=http://identity-service:8084`, `PAYMENT_BASE_URL=http://payment-mock:8085`, `MOCK_BASE_URL=http://integration-mock:8083`, `MOCK_HTTP_TIMEOUT=1s`, `KAFKA_BROKERS=kafka:9092`. OTLP defaults to `jaeger:4317`; telemetry service name is `orders-service`.

`Shop` resolves incoming gRPC `authorization: Bearer ...` against identity for every operation except public `catalog.list`. Request Actor and X-Demo-Actor never authorize requests. Roles and resource ownership are checked in the business command. Seed user IDs preserve existing records; newly registered accounts use identity-generated IDs. The legacy `CreateDemoOrder` RPC remains a separate technical fixture using integration-mock and the legacy Kafka topic.

Amounts are integer cents, commission is 10% rounded down per item line, quantities are 1..20. Checkout requires a customer-scoped idempotency key and locks inventory in sorted offer order. Reservations expire after 15 minutes; both replicas claim expired orders using row locks/SKIP LOCKED and release stock exactly once. Payment checks expiry under the order lock. Paid tickets do not expire. Expiry emits `order.expired`.

Payment/refund uses persisted provider IDs and stable keys `payment:<order_id>` / `refund:<order_id>`. Durable payment intent commits before authorization; if a response is lost or the order transaction rolls back, cancellation/expiry must complete the provider cancellation fence before releasing stock. The fence atomically refunds a successful effect or prohibits a delayed authorization. Durable refund intent similarly blocks redemption after an uncertain refund until cancel is retried successfully. Only the first explicit `MOCK_PROVIDER_ERROR` decline restores ticket usability; ambiguous database/network failures retain the fence. This mock workflow has no external provider or card input. Migration 006 explicitly marks existing pre-MVP PAID rows lacking payment_id as legacy fixtures. Only those rows retain the original MOCK_BASE_URL /mock/refunds adapter and receive a deterministic legacy-refund:<order_id> reference; no payment is fabricated or newly charged. Future rows default to the strict persisted-provider path, including missing provider records. The same refund intent fences redemption during uncertain legacy refunds.

Migrations 001–006 are serialized and versioned; existing data and applied migrations are retained. Business state/events commit with a transactional outbox on `BUSINESS_KAFKA_TOPIC=netdosuga.business.events.v1`. Publishers claim SKIP LOCKED rows and retry; delivery is at least once and consumers deduplicate event IDs. Legacy receipt+publish is sequential and lacks that guarantee.

HTTP `/healthz`, `/readyz`, `/metrics` and gRPC health remain available. New database sessions require read-write mode; readiness rejects standby or session-level read-only connections and resets the pool to retire pinned sessions after demotion. W3C traces include authentication, validation, SQL operations without parameters, transaction commit, payment/refund/reconciliation and outbox steps. Logs/span payloads use a bounded, typed allowlist; credentials, free text, user details and ticket codes are excluded. Fixed operation metrics supplement HTTP/gRPC metrics. Kafka outages queue business events without blocking readiness.
