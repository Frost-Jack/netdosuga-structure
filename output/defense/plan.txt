# НетДосуга: план защиты проекта

План выступления на 20 минут и справочник для демонстрации. Срез реализации: 30 октября 2026 года. Материал описывает проверенный локальный MVP; полный продуктовый backlog и production SLA не объявляются выполненными.

Основной тезис: проект реализует путь покупки билета и показывает, как сохранить корректность заказов при повторных запросах, конкуренции за места и отказах компонентов.

## Подготовка к защите

Запустите Docker Desktop в режиме Linux containers. Все команды PowerShell из справочника выполняются из корня репозитория netdosuga-structure. Сборку и полный набор тестов лучше закончить до начала выступления. На защите показывайте уже работающий стенд и сохранённые результаты; длительные отказные проверки запускайте отдельно от пользовательской демонстрации.

Обычный запуск требует одной команды Docker Compose. Предварительные setup/sync не нужны: приложения выполняют миграции, notification-worker подготавливает Kafka topics, PostgreSQL включает синхронный режим после первичного клонирования. Отдельных постоянных init-контейнеров нет. Тесты вынесены в отдельный Compose.

| Страница | Адрес | Что показать |
|---|---|---|
| Приложение | http://localhost:8080/ | Каталог, роли и покупка |
| Swagger API Gateway | http://localhost:8080/swagger/ | Контракты и Try it out |
| Jaeger | http://localhost:16686/ | Путь одного запроса |
| Kafka UI | http://localhost:8086/ | Топики, события, consumer groups |
| Grafana | http://localhost:3000/ | Частота, ошибки, длительность операций |
| Prometheus | http://localhost:9090/ | Исходные метрики и targets |

Все внешние порты опубликованы на 127.0.0.1. PostgreSQL, Kafka, gRPC и внутренние mock API доступны внутри сети Compose.

| Аккаунт | Роль |
|---|---|
| buyer@netdosuga.local | Покупатель |
| buyer2@netdosuga.local | Второй покупатель для проверки владения |
| vendor@netdosuga.local | Организатор |
| vendor2@netdosuga.local | Второй организатор |
| admin@netdosuga.local | Модератор |

В текущем локальном стенде начальный пароль этих аккаунтов: demo12345. Grafana: demo / demo12345. При первом создании аккаунтов пароль можно переопределить через MVP_SEED_PASSWORD. Существующие аккаунты не перезаписываются при рестарте. Значения platform/.env имеют приоритет над Compose defaults; изменение файла не меняет автоматически пароль уже созданной БД или Grafana.

Заранее подготовьте заявку на рассмотрении и два отдельных заказа. Один заказ нужен для погашения билета, второй для возврата: уже использованный билет отменить нельзя. После перезапуска Jaeger старые трассы исчезают, поэтому получите новую трассу оплаты непосредственно перед показом.

## 1. Назначение и границы MVP

Фраза для начала: «НетДосуга - сервис продажи билетов на городские активности. Организатор публикует предложение после модерации, покупатель резервирует места и оплачивает заказ, после чего получает билет. В проекте реализованы этот бизнес-сценарий, микросервисное взаимодействие, наблюдаемость и проверяемое восстановление после отказов. Платёжный провайдер и почта заменены моками».

Покупатель работает с каталогом, корзиной, резервом, оплатой, билетами и отменой. Организатор подаёт заявку, заполняет и публикует предложение, смотрит продажи и погашает билеты. Модератор одобряет или отклоняет заявки и имеет административный просмотр.

Одобрение заявки создаёт DRAFT. Публикация происходит отдельно после заполнения карточки. Платежи и письма имитируются, но пользователи, сессии, заказы, билеты и результаты mock-платежей сохраняются в PostgreSQL.

## 2. Архитектура и ответственность сервисов

| Компонент и каталог | Ответственность |
|---|---|
| api-gateway, gateway/ | HTTP API, интерфейс, Swagger, cookie и вызовы gRPC |
| identity-service, identity-service/ | Регистрация, вход, роли и сессии |
| orders-service, order-service/ | Заявки, предложения, корзина, резерв, заказы, билеты, outbox |
| payment-mock, payment-mock/ | Сохраняемые результаты оплаты/возврата и идемпотентность |
| notification-worker, notification-service/ | Kafka consumer, дедупликация, вызов почтового мока |
| mail-mock, integration-mock/ | Имитация уведомлений и прежние технические fixtures |
| platform/ | Compose, прокси, PostgreSQL, Kafka и наблюдаемость |

Путь синхронного запроса: браузер -> HTTP HAProxy -> один из двух gateway -> gRPC HAProxy -> один из двух orders-service. Gateway и orders обращаются к identity. Orders вызывает payment-mock. Приложения БД подключаются через PostgreSQL HAProxy к выбранному primary; он реплицирует WAL на standby.

Асинхронный путь: business_outbox -> publisher orders-service -> Kafka -> notification-worker -> mail-mock. Для диагностики сервисы отправляют трассы в Jaeger и предоставляют метрики Prometheus; Grafana показывает дашборды.

У каждого Go-сервиса собственные go.mod/go.sum, Dockerfile и контекст сборки. Каталоги можно перенести в отдельные Git-проекты, сохранив соседнее расположение для платформенной сборки. Общего родительского Go-модуля нет.

Каталог, корзина и заказы объединены в одном предметном сервисе. Это осознанное ограничение MVP: не создаётся сервис на каждую сущность, уменьшается количество распределённых транзакций.

Кластер и логическая БД общие. Владение схемами и таблицами разделено по ответственности, но сервисные права БД не изолированы. Это локальное упрощение, а не полная реализация database-per-service.

Открыть в проекте: docs/architecture.md и platform/compose.ha.yaml.

## 3. Живая демонстрация покупки

1. Модератор одобряет заранее подготовленную заявку.
2. Организатор открывает полученный черновик, задаёт описание, цену и количество мест, публикует предложение.
3. Покупатель добавляет предложение в корзину и создаёт заказ.
4. Покажите RESERVED и срок резерва: 15 минут. Это допущение MVP.
5. Выберите ошибку mock-платежа. Заказ не становится оплаченным, оплаченный билет не появляется.
6. Повторите оплату успешно. Заказ становится PAID, появляются билеты.
7. Организатор погашает билет. Повторное погашение отклоняется.
8. На другом заказе покажите отмену: mock-возврат, CANCELLED, отзыв билетов и восстановление доступности.

Фраза для объяснения: «Места резервируются при создании заказа. Билет выдаётся только после успешной оплаты. Погашение и отмена согласованы через состояние заказа, поэтому использованный билет вернуть нельзя».

Состояния заказа: RESERVED -> PAID / CANCELLED / EXPIRED. Оплаченный заказ также можно отменить при выполнении правил возврата. Состояния билета: VALID -> REDEEMED / REVOKED. Неоплаченный резерв истекает автоматически, оплаченные билеты этим таймером не отзываются.

Не пытайтесь показать возврат на уже погашенном билете как успешную операцию. Его отклонение является проверкой бизнес-правила.

## 4. API, Swagger и авторизация

В Swagger выполните POST /api/v1/auth/login, затем GET /api/v1/auth/session и GET /api/v1/shop/cart. Используйте Try it out и JSON с email/password. Браузер автоматически сохраняет и отправляет cookie. Вручную вводить nd_session в Authorize не требуется. POST /api/v1/auth/logout завершает сессию.

Swagger встроен в бинарник gateway. Контракт доступен по /openapi.yaml в JSON-формате. JavaScript, CSS и уведомления о лицензии локальные; дополнительный контейнер и CDN не нужны.

Пароли хешируются bcrypt. Identity создаёт случайный непрозрачный токен сессии, а в БД хранит его SHA-256. Gateway передаёт токен браузеру только в cookie nd_session с HttpOnly и SameSite=Lax. Сессия действует 24 часа; logout отзывает её. Для TLS-развёртывания предусмотрен COOKIE_SECURE; локальная демонстрация работает по HTTP.

Gateway передаёт сессию в orders через gRPC metadata. Orders независимо проверяет identity, роль и принадлежность ресурса. Публичная регистрация администратора запрещена. X-Demo-Actor и переданное клиентом поле actor не дают полномочий. Явные cross-site мутации отклоняются.

Фраза для объяснения: «Скрытая кнопка в интерфейсе не является защитой. Даже при ручном вызове API сервер проверяет роль и владельца объекта».

Контракт gRPC сейчас содержит общий RPC Shop с фиксированным перечнем операций. Конверт типизирован protobuf, предметное тело передаётся JSON. Отдельные типизированные сообщения для операций являются следующим шагом; нельзя заявлять, что все бизнес-поля уже типизированы protobuf.

Открыть: gateway/auth.go, order-service/auth.go, order-service/api/order.proto и gateway/api/openapi.yaml.

## 5. Транзакции, конкуренция и платежи

При создании заказа открывается транзакция PostgreSQL. Предложения блокируются SELECT ... FOR UPDATE, проверяется доступность, затем уменьшается остаток. Предложения блокируются в одном порядке по ID, что снижает риск взаимных блокировок. Транзакционная advisory-блокировка покупателя сериализует его изменения корзины и checkout между репликами сервиса.

Клиент передаёт Idempotency-Key. В БД действует UNIQUE(customer_id, idempotency_key). Повтор создания заказа с той же парой возвращает существующий заказ. Это не автоматический повтор всех HTTP-мутаций и не глобальная exactly-once гарантия.

Деньги хранятся целыми копейками. Так исключаются ошибки представления сумм двоичными дробями. Комиссия MVP составляет 10% и рассчитывается целочисленно по строкам заказа.

Таймаут оплаты не доказывает отсутствие списания: провайдер мог сохранить результат, а ответ потеряться. До внешнего вызова сохраняется payment intent. Mock хранит результат по стабильному ключу payment:<order_id>; возврат использует refund:<order_id>. Повтор возвращает сохранённый идентификатор, несовместимый повтор не должен создавать новый эффект.

При отмене неопределённой оплаты mock атомарно запрещает позднюю оплату и возвращает уже проведённую, если она была. Места освобождаются после разрешения этой ситуации. При неопределённом возврате refund intent блокирует погашение билетов до завершения повторной отмены. Общий HTTP 503 не считается доказательством отсутствия эффекта; только явно определённый отказ до эффекта может безопасно снять соответствующую блокировку первого отказа.

Фраза для объяснения: «Я различаю отказ операции и неизвестный результат операции. Таймаут или HTTP 503 ещё не доказывает, что списания не было».

Отмена и погашение синхронизируются блокировкой заказа. Использованный билет запрещает отмену; повторное погашение не меняет результат. Старая fixture-оплата без нового provider record выделена миграцией 006 в отдельный совместимый путь возврата; новые заказы не получают такой обход.

Компромисс: внешний платёжный вызов пока выполняется при открытой транзакции заказа. Настоящий провайдер потребует фоновой сверки результатов, обработки webhook и сокращения времени удержания блокировок. Нельзя обещать готовность к любому банковскому API.

Открыть: order-service/business.go, order-service/payment_expiry.go, order-service/migrations/ и payment-mock/main.go.

## 6. Kafka и transactional outbox

Проблема прямой последовательности «сохранить заказ в PostgreSQL, затем отправить событие в Kafka»: сбой между действиями оставляет заказ без события. В бизнес-сценарии заказ и запись business_outbox фиксируются одной SQL-транзакцией.

Publisher выбирает неопубликованные строки через FOR UPDATE SKIP LOCKED. Два экземпляра могут брать разные строки. После подтверждения Kafka сохраняется published_at. При сбое между Kafka ACK и фиксацией published_at событие может быть опубликовано повторно.

Consumer проверяет event_id, обрабатывает событие и фиксирует offset после успешной обработки. Повторные сообщения дедуплицируются через PostgreSQL. Некорректные сообщения записываются в quarantine, чтобы не блокировать поток навсегда.

В Kafka UI покажите netdosuga.business.events.v1. Типы бизнес-событий: order.created, order.paid, order.cancelled, order.expired, ticket.redeemed. Отдельный старый netdosuga.demo.orders.v1 нужен для технических fixtures и регрессии.

Гарантия доставки: at-least-once с дедупликацией. Нельзя называть всю цепочку end-to-end exactly-once: отправка внешнего письма и SQL-отметка обработки не атомарны. Доставка ровно одного уведомления в конкретном отказном тесте не отменяет эту границу.

При недоступной Kafka бизнес-заказ и outbox сохраняются. После восстановления брокера publisher продолжает доставку. Старая техническая ручка /api/v1/demo/orders не обладает гарантиями бизнес-outbox.

Открыть: order-service/business.go, notification-service/business.go, notification-service/topics.go.

## 7. Балансировка и PostgreSQL HA

HTTP HAProxy распределяет запросы между двумя gateway. gRPC HAProxy распределяет вызовы между двумя orders-service. PostgreSQL HAProxy направляет соединения на явно выбранный primary. Заголовки X-Gateway-Instance и X-Order-Instance показывают обслужившие запрос экземпляры. HAProxy выполняет функции локальной замены балансировщиков F5 из исходной схемы.

PostgreSQL использует физическую streaming-репликацию WAL. synchronous_commit=remote_apply в штатном синхронном режиме означает ожидание применения записи на реплике до подтверждения транзакции. Цена: дополнительная задержка и возможное ожидание записи при недоступности синхронной реплики.

Ручное переключение: остановить старый primary и подтвердить fencing; продвинуть standby; изменить маршрут прокси; временно работать с одной копией; пересоздать прежний primary через pg_basebackup; вернуть синхронный режим. Старый PGDATA сохраняется в его томе перед rejoin. Обычный запуск старого writable primary после переключения запрещён до явного rejoin.

Это не автоматический кластер с referee/quorum. Автоматическое включение sync после начального клонирования не равно автоматическому failover. После failover до rejoin система работает в деградированном режиме с одной копией PostgreSQL.

В интеграции была найдена ошибка: после смены Docker IP соединение могло остаться привязано к standby, а простой Ping отвечал успешно. Исправление использует writable-проверки и target_session_attrs=read-write; read-only соединения удаляются из пула, прокси закрывает сессии отключённого backend.

Полный verify-ha.ps1 временно останавливает приложения, Kafka и PostgreSQL, меняет текущий primary и возвращает реплику. Запускайте его отдельно от ручной демонстрации. На короткой защите достаточно показать сохранённый отчёт и один пример отказа gateway с восстановлением.

Открыть: platform/ha/gateway.cfg, platform/ha/order.cfg, platform/ha/postgres.cfg, platform/scripts/ha-postgres.ps1, order-service/internal/observe/database.go.

## 8. Наблюдаемость и движение запроса

После оплаты раскройте диагностику последнего действия в интерфейсе и перейдите к трассе Jaeger. Последующие GET-обновления списка не заменяют trace последней мутации.

Разберите путь: HTTP-запрос -> gRPC -> operation.orders.pay -> authentication.resolve -> SQL -> payment.authorize -> шаги mock-провайдера -> transaction.commit и outbox.enqueue в соответствующей части транзакции. Outbox переносит W3C trace context в Kafka, consumer продолжает обработку с этим контекстом. Диаграмма трассы показывает фактическую вложенность, а не только перечисление сервисов.

| Инструмент | На какой вопрос отвечает |
|---|---|
| Jaeger | Где конкретный запрос потратил время или завершился ошибкой? |
| Prometheus / Grafana | Как меняются частота, ошибки и длительность операций? |
| JSON-логи | Какие события произошли и как найти их по trace_id? |
| Kafka UI | Какие сообщения опубликованы и как работает consumer? |

app.request и app.response содержат только разрешённые диагностические поля. Пароли, токены, email, свободный пользовательский текст и коды билетов исключены. Ограничены длины и количество элементов. SQL spans показывают операции без значений параметров. Идентификаторы заказов и пользователей не включаются в labels метрик, чтобы не создавать неограниченную cardinality.

Jaeger хранит трассы в памяти. После рестарта создайте новую демонстрационную операцию. Логи доступны через Docker stdout; централизованного долговременного log storage пока нет.

## 9. Проверки, ограничения и развитие

Подтверждённый набор: 38 smoke-проверок, 8 групп business-проверок и 7 MVP-проверок. Отдельно выполнены 12 HA-проверок, SQL-регрессии конкуренции, потерянных ответов, откатов и восстановления read-only соединений. Чистый запуск на пустых томах и полный рестарт с сохранением данных прошли. Swagger проверен цепочкой login -> session -> защищённая cart -> logout.

Эти числа относятся к зафиксированным прогонам, а не являются обещанием текущего состояния после любых будущих изменений. Go unit tests входят в Docker build. Отдельный Compose запускает сетевые наборы последовательно и возвращает ненулевой exit code при ошибке. SQL-тесты используют отдельные тестовые схемы/БД и не равны этим 53 сетевым проверкам.

Открыть: docs/verification.md, docs/mvp-review.md и docs/architecture-status.md. Отчёты тестов расположены в platform/test-results/.

Ограничения, которые следует назвать:

- Все контейнеры работают на одном компьютере. Проверен отказ компонентов, а не потеря хоста или дата-центра.
- Kafka и каждый HAProxy имеют по одному экземпляру; они остаются точками отказа.
- PostgreSQL failover ручной. Репликация не заменяет резервное копирование.
- Нет настоящего платёжного провайдера, SMTP и фонового reconciliation неопределённых возвратов.
- Не завершены production TLS, управление секретами, отдельные права БД и проверенное backup/restore.
- Не подтверждены нагрузочный SLA и полная кроссбраузерная сертификация.
- Антифрод, ClickHouse, рейтинги, бонусы, промокоды, динамические цены и ряд других функций остаются в backlog.
- Общая политика rate limiting gateway, TTL хранения idempotency keys и optimistic version заказа пока не реализованы полностью.

Ближайшие шаги: резервное копирование с восстановлением на тестовом стенде; TLS, секреты и сервисные роли БД; контракт реального провайдера с webhook/reconciliation; устранение одиночных точек отказа; нагрузочные испытания. Очерёдность и объём зависят от требований развёртывания.

Фраза для завершения: «Получен воспроизводимый MVP полного пути покупки. Его поведение проверено при повторных запросах, конкуренции за места, ошибках платежей и отказах компонентов. Следующий этап - подключение реальных интеграций и проверка эксплуатационных требований production».

## Вопросы комиссии и короткие ответы

| Вопрос | Ответ |
|---|---|
| Почему микросервисы? | Разделены независимые ответственности и сетевые границы. Gateway и orders масштабируются отдельно. Сервис на каждую сущность не создавался. |
| Почему общая БД? | Это локальное упрощение MVP. Владение данными разделено в коде, но права и физическая изоляция требуют дальнейшей работы. |
| Зачем Kafka, если есть gRPC? | gRPC нужен для синхронного ответа, Kafka - для асинхронной обработки событий и восстановления после временной недоступности потребителя. |
| Что произойдёт при двойном нажатии «Оплатить»? | Проверяется состояние заказа. Mock использует стабильный ключ и возвращает сохранённый результат; повтор не создаёт новые билеты. |
| Что будет при остановке Kafka? | Заказ и outbox сохранятся в БД. После восстановления брокера публикация продолжится. Это проверено отказным тестом. |
| Почему не JWT? | Центральные сессии позволяют отзывать доступ при logout. Цена: обращения к identity и зависимость от его доступности. |
| Можно ли вернуть использованный билет? | Нет. Отмена и погашение синхронизируются блокировкой заказа и проверкой состояний билетов. |
| Репликация заменяет backup? | Нет. Ошибочное удаление тоже реплицируется. Для восстановления на прошлый момент нужны резервные копии и проверка восстановления. |
| Доказана ли exactly-once доставка письма? | Нет. Используются at-least-once и дедупликация event_id, но внешний вызов и SQL-отметка не атомарны. |
| Все ли бизнес-поля типизированы protobuf? | Нет. Shop имеет типизированный конверт с JSON-телом. Разделение на отдельные типизированные RPC относится к дальнейшему развитию. |
| Что первым делать для production? | Backup/restore, TLS и секреты, права БД, платёжный контракт со сверкой, затем устранение точек отказа и нагрузочные проверки. |

## Как пользоваться справочником команд

В HTML строка поиска отбирает команды по названию, тексту, назначению и ключевым словам. Например: «запуск», «логи», «репликация», «Kafka», «вход», «отказы». Кнопка копирования только помещает текст в буфер, ничего не запускает. Команды PowerShell выполняются в терминале из корня проекта; HTTP-операции выполняются в Swagger и не являются shell-командами.

Перед запуском смотрите ожидаемый результат и последствия. stop, failover, rejoin и verify-ha изменяют состояние стенда и временно нарушают доступность. Для обычной остановки используйте stop; команды удаления томов в справочник намеренно не включены. Тесты создают собственные демонстрационные записи, поэтому после них в каталоге могут появиться тестовые предложения.

PDF содержит тот же план и полный каталог команд как статический справочник. В HTML поиск интерактивный, страница работает локально без CDN и сборки. Ссылки localhost работают только при запущенной системе. Ссылки на исходники требуют сохранить расположение папок проекта.
