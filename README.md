# НетДосуга

Локальный MVP городской афиши и билетной кассы на Go, gRPC и Kafka. Организатор подаёт заявку, модератор одобряет её, организатор заполняет и публикует событие. Покупатель входит в аккаунт, собирает корзину, резервирует места и получает билеты после тестовой оплаты. Есть погашение билета и возврат до использования.

Платежи и почта имитируются. Пользователи, сессии, заказы, билеты и результаты платёжного mock сохраняются в PostgreSQL. HA-вариант запускает два gateway, два сервиса заказов и синхронную реплику БД.

## Запуск одной командой

Нужен работающий Docker Desktop в режиме Linux containers. Выполните из корня проекта:

```powershell
docker compose -f platform/compose.ha.yaml up -d --build --wait
```

Предварительные setup и sync не нужны: Compose использует локальные значения по умолчанию, приложения выполняют миграции, PostgreSQL включает синхронную репликацию после клонирования. Отдельных init-контейнеров нет. Первая сборка требует сети и занимает больше времени; последующие используют кеш.

Существующий `platform/.env` имеет приоритет. Сохраняйте его вместе с существующими томами: новый пароль в файле не меняет пароль уже созданной БД или Grafana. Базовый и HA-вариант занимают одинаковые порты; если раньше запускали базовый, сначала остановите его: `docker compose -f platform/compose.yaml stop`.

| Адрес | Для чего |
|---|---|
| [localhost:8080](http://localhost:8080) | Афиша и кабинеты |
| [localhost:8080/swagger/](http://localhost:8080/swagger/) | Swagger UI API Gateway: контракты и выполнение запросов |
| [localhost:3000](http://localhost:3000) | Grafana: `demo` / `demo12345` в текущем стенде |
| [localhost:16686](http://localhost:16686) | Jaeger, движение запроса между сервисами и внутри методов |
| [localhost:8086](http://localhost:8086) | Kafka UI: топики, события и consumer groups, просмотр без изменения |
| [localhost:9090](http://localhost:9090) | Prometheus |

Все опубликованные порты доступны только на loopback. БД, Kafka, gRPC и mock API доступны внутри сети Compose.

Swagger встроен в gateway и не требует дополнительного контейнера или доступа браузера к CDN. Исходный контракт доступен по `/openapi.yaml` (OpenAPI в JSON-формате). Для защищённых запросов сначала выполните `POST /api/v1/auth/login` через **Try it out** или войдите в основной интерфейс на том же адресе. Браузер передаст cookie сессии автоматически; вручную копировать токен не нужно. Роли и ограничения API действуют также для запросов из Swagger.

## Аккаунты и демонстрация

Начальный пароль аккаунтов: `demo12345`, если при первом создании не задан другой `MVP_SEED_PASSWORD`.

| Аккаунт | Роль |
|---|---|
| `buyer@netdosuga.local` | Покупатель |
| `buyer2@netdosuga.local` | Второй покупатель для проверки владения |
| `vendor@netdosuga.local` | Организатор |
| `vendor2@netdosuga.local` | Второй организатор |
| `admin@netdosuga.local` | Модератор |

Можно зарегистрировать своего покупателя или организатора. Администратор через публичную регистрацию не создаётся. Начальные аккаунты не перезаписываются при рестарте.

1. Войдите организатором, откройте «Заявки» и отправьте событие на рассмотрение.
2. Выйдите и войдите модератором, одобрите заявку. Появится черновик.
3. Организатор заполняет описание, цену и количество мест в «Мои события», затем публикует событие.
4. Покупатель добавляет события в корзину и создаёт заказ. Неоплаченный резерв действует 15 минут.
5. В «Мои билеты» попробуйте ошибку тестовой оплаты, затем успешную оплату. Откройте детали и скопируйте код билета.
6. Организатор погашает билет в «Продажах». Повторное погашение отклоняется. Для проверки возврата используйте другой, ещё не погашенный билет.

Повтор оплаты возвращает сохранённый результат mock-провайдера. Карточных данных нет, деньги не списываются. Комиссия 10% и резерв 15 минут являются допущениями локального MVP.

## Автотесты отдельным Compose

После запуска системы:

```powershell
docker compose -f platform/compose.tests.yaml up --abort-on-container-exit --exit-code-from tests
```

Один тестовый контейнер последовательно запускает технический smoke, бизнес-сценарии и проверки MVP. Ненулевой exit code означает ошибку. Отчёты сохраняются в `platform/test-results/`; тесты создают собственные записи. Go-тесты выполняются также при сборке каждого сервиса.

Дополнительная проверка отказов временно останавливает приложения, Kafka и primary PostgreSQL, затем восстанавливает их:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File platform/scripts/verify-ha.ps1
```

Она запускается отдельно от ручной демонстрации и меняет текущий primary. Это эксплуатационная проверка, для обычного запуска скрипт не нужен. Подтверждённые результаты записываются в [отчёт проверки](docs/verification.md), замечания независимых ревью и их исправления — в [журнал ревью](docs/mvp-review.md).

## Диагностика запроса

В интерфейсе раскройте диагностику последнего действия и перейдите по ссылке на Jaeger. Последующие обновления списка не заменяют trace последней мутации. Внутри трассы раскройте `operation.orders.pay`: видны проверка сессии, SQL, `payment.authorize`, шаги mock-провайдера и фиксация транзакции. Outbox продолжает контекст в Kafka и обработчике уведомлений.

Атрибуты `app.request` и `app.response` содержат очищенные поля: операцию, идентификатор заказа/предложения, количество, сумму и статус. Пароли, cookie, токены, email и коды билетов туда не записываются. Grafana показывает частоту, ошибки и длительность операций. JSON-логи можно читать командой:

```powershell
docker compose -f platform/compose.ha.yaml logs --tail 100 gateway-a order-a identity-service payment-mock notification-service
```

## Остановка и повторный запуск

```powershell
docker compose -f platform/compose.ha.yaml stop
docker compose -f platform/compose.ha.yaml up -d --no-build --wait
```

Тома и данные сохраняются. `down -v` удаляет их, поэтому для обычной остановки его не используйте. Jaeger хранит трассы в памяти. Ручной failover и возврат реплики описаны в [инструкции HA](platform/HA.md); бывший primary нельзя самостоятельно запускать до rejoin.

## Структура и границы MVP

`gateway/`, `identity-service/`, `order-service/`, `payment-mock/`, `notification-service/`, `integration-mock/` и `platform/` предназначены для отдельных Git-проектов. У Go-сервисов независимые modules и build contexts, общего родительского модуля нет.

[Матрица требований](docs/architecture-status.md) отделяет реализованное от оставшегося. Автоматического referee, антифрода, ClickHouse, настоящих платежей/SMTP, TLS, backup/restore и подтверждённого production SLA пока нет. Следующие технические шаги: интеграция настоящего провайдера, роли БД по сервисам, резервное копирование с проверкой восстановления и централизованное хранение логов.

Подробности: [архитектура](docs/architecture.md), [ADR](docs/adr.md), [план MVP](docs/mvp-plan.md), [backlog](docs/backlog.md), [эксплуатация](docs/operations.md).
